# Agent Context Format (ACF) 1.4

ACF is a format for keeping agent context in a repository: small typed markdown documents with YAML frontmatter, loaded in layers, with an owner, a template and machine-checkable rules for each document type. It is designed for software projects. ACF is a standalone format; it is not a profile of any other format. Interoperability with the Open Knowledge Format (OKF) is provided by an adapter (section 1). The key words MUST, SHOULD and MAY are used as in RFC 2119.

Reference implementation: `ackit` (this repository). The type registry the validator reads, `src/ackit/data/types.yaml`, is the machine-readable form of section 5; `docs/DOC-TYPES.md` is generated from it. Changes to field names between versions are listed in `docs/CHANGELOG.md`.

## 1. Interoperability

ACF's design borrowed from OKF v0.2 (a bundle of markdown documents with frontmatter, trust and staleness fields, reserved `index.md` and `log.md`), but depends on it for nothing. Where ACF names a field differently, the adapter translates.

- `ackit export --okf <out>` writes an OKF v0.2 bundle from an ACF bundle.
- `ackit import --okf <in> --dest <bundle>` reads an OKF v0.2 bundle into an ACF bundle.

Field mapping: `review_by` <-> `stale_after`; `sources[].ref` <-> `sources[].resource`; root index `acf_version` plus `okf_version: "0.2"` on export. `type`, `title`, `description`, `tags`, `generated`, `verified`, `status` and all other keys pass through unchanged. OKF only knows `draft`, `stable` and `deprecated`: on export every ACF status is mapped to one of these and the original is kept in `acf_status`, which import restores. The role overlay `roles/` is stored under `.acf/roles/` in the OKF bundle.

What cannot round-trip is listed in `docs/INTEROP.md`: OKF concepts without a `type` are skipped; ACF rules (sections, sign-off order, completeness) are not OKF concepts and are checked again after import; OKF statuses without `acf_status` are mapped to the nearest ACF status; the OKF `resource` field of a concept itself is preserved as an unknown key.

## 2. Conformance

- **ACF-conformant**: `ackit validate` reports no errors. Warnings are allowed.
- **ACF-strict**: `ackit validate --strict` reports nothing. Recommended for CI on stable branches.
- Tools MUST preserve unknown frontmatter keys when rewriting a document.

## 3. Layers

ACF has three layers; an agent loads them in order and stops as soon as it has enough (progressive disclosure).

1. **Entry** - `AGENTS.md` at the bundle root, `type: entry`. Always loaded, therefore small (default budget 150 lines, `agents_md_max_lines`). Holds the project line, build and verify commands, the never-break rules each with a Why, and a "load on demand" table with one row per document. A repository MAY symlink its root `AGENTS.md` (or `CLAUDE.md`) to it; `ackit init --link-entry` does so.
2. **Index** - `index.md`, generated by `ackit index --write`: every concept with its description, grouped by kind.
3. **Records** - everything else, loaded on demand: knowledge docs (product, architecture, modules, rules, reference), work items, and the history (journals, sessions, reviews, evidence, handoffs, incidents, decisions).

### Reserved files

`index.md` and `log.md` are reserved names, not concepts. `index.md` has no `type`; the root one carries `acf_version` in its frontmatter and lists every concept under headings, one bullet link per concept with its description. `log.md` holds `## YYYY-MM-DD` headings, newest first, with bullet entries of what changed in the bundle.

### Layout

```
context/
  AGENTS.md  index.md  log.md  ackit.yaml
  product.md  tech-stack.md  workflow.md  architecture.md  responsibilities.md
  rules/<slug>.md                 R-<slug>
  modules/<slug>.md               M-<slug>              (large repos)
  work/epics/E-001-<slug>.md
  work/features/F-001-<slug>.md                         (tier small)
  work/features/F-002-<slug>/feature.md + 01-analysis.md ... 06-journal.md   (tier large)
  work/tasks/T-001-<slug>.md  work/issues/I-001-<slug>.md
  decisions/ADR-0001-<slug>.md  incidents/INC-001-<slug>.md  journals/<name>.md
  sessions/<author>/<branch>.md + current.md
  reviews/  evidence/  handoffs/  reference/  design/  runbooks/
  roles/<role>/                   overlay (section 7), not concepts
```

| Repository | Required documents | Optional |
|---|---|---|
| **Small** (single module) | `AGENTS.md`, `index.md`, `log.md`, `product`, `tech-stack`, `workflow`, `architecture`, `responsibilities` | rules, decisions, journals, work items, everything else |
| **Large** (several modules, or a monorepo) | the small set, plus one `module` document per module | per-module rules (`applies_to` / `modules` narrow them), epics, runbooks |

`ackit init` chooses the size from module discovery and asks only when it cannot infer.

## 4. Frontmatter

Keys common to all types (see each type for what else it requires):

| Key | Meaning |
|---|---|
| `type` | required; section 5 |
| `title` | required |
| `description` | one line; required for product, tech-stack, reference |
| `id` | stable identifier for types with ids (section 11) |
| `status` | from the type's status set (section 6) |
| `generated: {by, at}` | who wrote the current content, and when; actors are `<producer>/<version>`, `human:<id>` or `process:<id>`. Missing is a warning (ACF023) |
| `verified: [{by, at}]` | confirmations, independent of `generated.at`; a `human:<id>` actor means human-reviewed |
| `review_by` | ISO 8601 datetime with offset: the time by which a human must re-review; at or after it the document is stale |
| `sources: [{ref, ...}]` | provenance: where the content came from (`ref` is a path or URL; optional `title`, `author`, `last_modified`) |
| `history: [status, ...]` | optional ordered statuses; when present the transitions are checked. `ackit new` writes the initial status for work types and `ackit status` appends to it |
| `tags` | list |

Any other key is allowed and preserved.

Optional keys defined by a type (listed per type under "Optional frontmatter" in `docs/DOC-TYPES.md`):

| Key | On | Meaning |
|---|---|---|
| `external_id` | epic, feature, task, issue | non-empty string: the key of the same work in an external tracker (`PROJ-123`). A ticket in any tracker is not a separate type; it maps to a work item through this key (ACF034) |
| `points` | task, issue | integer estimate in the configured scale (default `[1, 2, 3, 5, 8]`); see "Points" below (ACF031, ACF032) |
| `runs` | task, issue | ordered list of run records, one per attempt at the item; see "Runs" below (ACF033) |

### Points

`points` is an integer that MUST be in the scale. The scale and two limits are set in `ackit.yaml`: `points: {scale: [1, 2, 3, 5, 8], auto_start_max: 2, signoff_max: 5}` (these are the defaults). An item with points above `signoff_max` MUST be split before it is `ready` or `in-progress` (ACF032; it may stay `draft`, `blocked` or `cancelled`). An item with points above `auto_start_max` MUST carry `signoff: {by, at}` before it leaves `draft` (ACF027), the same pattern as a small feature; at or below it a tool MAY start the item without a person. How the estimate is computed is not part of ACF.

### Runs

`runs` is a list; each record is a mapping `{id, at, outcome, tokens?, turns?, commit?, by?}`: `id` a string unique within the list, `at` an ISO 8601 datetime, `outcome` a free string, `tokens` and `turns` non-negative integers, `commit` a string, `by` the agent or tool that did the run (free text). Other keys in a record are preserved. Records are appended, oldest first, and past records are not edited.

## 5. Document types

| Type | Directory | Purpose | Id |
|---|---|---|---|
| `entry` | root | the small always-loaded file | - |
| `product` | root | purpose, users, goals, non-goals | - |
| `tech-stack` | root | languages, frameworks, infrastructure, conventions | - |
| `workflow` | root | build/test/lint commands, branching, definition of done | - |
| `architecture` | root | components, data flow, constraints | - |
| `module` | `modules/` | one module of a large repo | `M-<slug>` |
| `rule` | `rules/` | a never-break rule with its Why | `R-<slug>` |
| `responsibility` | root | RACI per area and document type | - |
| `epic` | `work/epics/` | a body of work | `E-NNN` |
| `feature` | `work/features/` | a deliverable; `tier: small` one doc, `tier: large` a staged folder | `F-NNN` |
| `feature-stage` | `work/features/F-NNN-*/` | analysis, design, plan, tasks, test-plan | - |
| `task` | `work/tasks/` | one session of work under a feature | `T-NNN` |
| `issue` | `work/issues/` | bug or defect and its fix | `I-NNN` |
| `incident` | `incidents/` | a failure: symptom, cause, fix, checks | `INC-NNN` |
| `decision` | `decisions/` | ADR: context, options, decision, why, consequences | `ADR-NNNN` |
| `journal` | `journals/` | append-only decisions and corrections | - |
| `session` | `sessions/` | per-branch log; Done / Faced / Decisions / Build / Next / Blockers | - |
| `session-index` | `sessions/` | rolling one line per session | - |
| `review` | `reviews/` | findings of a code, security or test review of one item | - |
| `test-evidence` | `evidence/` | what was run and what it showed | - |
| `handoff` | `handoffs/` | hand a finished item to a person or the next agent | - |
| `design-spec` | `design/` | UX/UI flows, screens, states, accessibility | `D-<slug>` |
| `runbook` | `runbooks/` | operational procedure with rollback | `RB-<slug>` |
| `reference` | `reference/` | stable facts loaded on demand | - |
| `ticket-resolution` | any (`dir: ""`) | one resolved support ticket: what was wrong, the resolution type (1 to 6), the tickets, the checks made (1.4) | - |
| `issue-pattern` | any (`dir: ""`) | a recurring kind of support issue and how to recognise it (1.4) | - |
| `platform-behaviour` | any (`dir: ""`) | how the platform behaves, written by a developer or support agent (1.4) | - |

For each type `docs/DOC-TYPES.md` gives: required frontmatter, required body sections, status set, and **ownership** - who writes it, who reviews it, who signs it off, and when it must be updated. Ownership is also materialised in the project's `responsibilities.md`.

The three support types (1.4) have `dir: ""`, so ACF022 does not place them; `resolution_type` is an enum of the integers 1 to 6, compared by type and value (`1.0` and `true` are not `1`), and `ackit new` does not default a numeric enum. A bundle that already holds pages of these type names gets their checks from 1.4 on.

**Vocabularies (1.4).** `vocabularies` in `ackit.yaml` is a mapping of vocabulary name to a source, each with exactly one of: `values` (a list), `source_file` + `key_path` (a local file, optionally `id_key`; a read the adopter opts into) or `of_type` (the ids of the documents of a type). A type binds a field to a vocabulary with `vocab: {field: vocabulary}`; a value of that field (a string or a list) not in the vocabulary is ACF043, an unusable `vocabularies` entry is ACF044. Absent block: nothing changes.

A bundle MAY add or change types under `types:` in `ackit.yaml` (same schema as the registry) without code changes.

### Work hierarchy

`epic` (done when every child feature is done) -> `feature` -> `task`; `issue` is a bug and may reference a feature. A **ticket** in an external tracker is not a type: it maps to a feature, task or issue through `external_id`. A **job** (one run of a task by an agent) is not a type either: it is a `runs` record on the task. A **small feature** is one document with sections Goal, Acceptance criteria, Design, Plan, Test plan and a `signoff` before it leaves `draft`. A **large feature** is a folder: `feature.md` plus `01-analysis`, `02-design`, `03-plan`, `04-tasks`, `05-test-plan`, `06-journal`. Each stage carries `status: draft|signed-off` and `signoff: {by, at}`; a stage MUST NOT be signed off while an earlier one is not. A large feature MAY be `ready` or `in-progress` only after analysis through tasks are signed off, and `in-review` or `done` only after test-plan is too.

### Journal, decision record, session

- **Journal**: entries `## YYYY-MM-DD - kind: title` (kind: decision, correction, finding, note), newest first. A past entry is never edited; a correction is a new entry. Living documents state only current truth; history lives here.
- **Decision record**: sections Context, Options (at least two), Decision, Why, Consequences. Status `proposed -> accepted | rejected`, then `superseded` or `deprecated`. An accepted record is not edited: write a new one with `supersedes`; the old one gets `superseded_by` and status `superseded`.
- **Session entry**: heading `## YYYY-MM-DD (Day, Www) - branch @ sha - title` with bold labels Done, Faced, Decisions, Build, Next, Blockers. The index lines are `- YYYY-MM-DD - branch - title - [entry](path)`. The sha is 7 to 40 hex characters, or the word `none` for an entry not tied to a commit; ACF045 checks the whole heading and ACF021 the date and the labels. The day is the English three-letter name (Mon to Sun) and the week is W01 to W53; the rule applies to sessions in author workspace folders too, and, being a warning, fails `ackit validate --strict` for a bundle whose headings differ.

## 6. Lifecycle

| Set | Statuses | Used by |
|---|---|---|
| doc | draft -> stable -> deprecated | entry, product, tech-stack, workflow, architecture, module, rule, responsibility, journal, reference, design-spec, runbook |
| work | draft -> ready -> in-progress -> in-review -> done; blocked, cancelled | epic, feature, task, issue |
| decision | proposed -> accepted -> superseded / deprecated; proposed -> rejected | decision |
| incident | open -> mitigated -> resolved -> closed | incident |
| record | draft -> final | session, review, test-evidence, handoff |
| stage | draft <-> signed-off | feature-stage |

When `history` is present, each consecutive pair MUST be a legal transition and the last entry MUST equal `status`. `ackit status <id-or-path> <new-status>` checks a move against this table, appends to `history` (creating it from the current status when missing) and refuses an illegal move, listing the legal next statuses.

**An on-hold status.** The core `work` set has `blocked` for a pause. A bundle that wants a separate `on-hold` (a deliberate pause, not a block) declares it, with no code change, because a bundle's `status_sets` replace a set by name. The block, tested in `tests/test_acf045_session_heading.py`, makes `in-progress -> on-hold -> in-progress` legal and refuses `on-hold -> done`:

```yaml
status_sets:
  work:
    values: [draft, ready, in-progress, on-hold, blocked, in-review, done, cancelled]
    initial: draft
    transitions:
      draft: [ready, cancelled]
      ready: [in-progress, draft, cancelled]
      in-progress: [in-review, on-hold, blocked, cancelled]
      on-hold: [in-progress, cancelled]
      blocked: [in-progress, cancelled]
      in-review: [done, in-progress]
      done: []
      cancelled: []
    human_verified: []
```

**Done means evidence.** A `feature` at `done` MUST have a `test-evidence` record with `result: pass`, a `review` with `verdict: approve`, and a `journal` whose `about` is the feature. An `issue` at `done` needs evidence and review. An `epic` at `done` needs every feature done.

## 7. Roles and profiles

A **role profile** describes a working role; it is separate from stack packs (section 8). Roles are directories:

```
<role>/role.yaml        name, title, description, owns, checklists, gates, tools_allowed, [extends]
<role>/prompt.md(.j2)   the prompt TEMPLATE (Jinja2)
<role>/rules.md         binding rules
<role>/checklist.md     verifiable checks  "- [ ] **ID-NN** text"
<role>/outputs.md       which documents the role writes, in what format
<role>/prompt-guide.md  how to write or tune this role's prompt
<role>/wrap-up.md      OPTIONAL: what an agent is told when an orchestrator stops its run at the budget (finish the change, list what is left)
```

`role.yaml`: `suggested_agent` (optional) is a vendor-neutral hint about what kind of agent should play the role; `owns` is a list of document types the role writes; `checklists` the checklist files required of it (default `[checklist.md]`); `gates` the gates it takes part in (`start`, `handoff`); `tools_allowed` is advisory text carried into the prompt; `extends` names a role whose missing parts this role inherits.

**Built-in roles**: developer, tester, security (security reviewer), reviewer (code reviewer), business-analyst, architect, designer (UX/UI), devops, support (1.4: owns the three support types, drafts only what the evidence supports, asks `Question:` lines for the rest, runs read-only queries only); optional planner and maintainer.

**Resolution** (per part, first found wins): the bundle overlay `roles/<role>/<part>` -> the kit default -> the parent named by `extends`. So a team can (a) use a built-in as is, (b) override any single part per repository by dropping a file in `roles/<role>/`, or (c) define a new role with `ackit role new <name>`, which scaffolds all six files from the role template. Overlay files MAY omit frontmatter; if present it is ignored. `wrap-up.md` is optional in both places (the kit ships none); `ackit prompt <role> --part wrap-up` prints it, `ackit role path <role>` prints the overlay folder.

**Suggested agent.** `suggested_agent: {capability, reasoning, independent_of}`, all optional keys except `capability` when the field is present. `capability` is a tier: `high` (most capable, for work where mistakes are costly), `standard`, or `fast` (cheap, for routine work). `reasoning` is `deep` or `normal`. `independent_of` names another role whose work this role judges: the orchestrator should use a different agent or model instance than the one that played that role (for example reviewer independent of developer). The field names no vendor or model; an adopter maps tiers to real models in its own configuration (`adopters/example/agent-map.yaml`). Tools use it as the role-default level when choosing an agent, below any explicit user choice. Built-in defaults: developer high; architect, security and planner high with deep reasoning; reviewer high, independent of developer; tester, business-analyst, designer and devops standard; maintainer fast. `ackit role list` and `ackit prompt <role> --explain` show it; `ackit role list --json` gives the profiles to tools. The `reviewer` and `security` outputs also define the machine-readable findings object (`verdict`, `findings[]` with `severity` blocking|major|minor|info, `file`, `line`, `title`, `detail`) that an orchestrator parses.

**Validation (ACF030)**: a custom role or an overridden profile must have `name`, `description`, `owns` (known types), `gates` (known gates); `suggested_agent`, when present, uses only the keys above with valid values and a known `independent_of` role other than itself; prompt, rules, checklist and outputs must exist; every listed checklist must contain at least one `- [ ] **ID-NN**` item; the prompt must be a valid template.

**Prompt generation.** `ackit prompt <role> --item <id>` renders the role's prompt template with: the project line; the stack summary and workflow commands; the blocking rules that apply to the role and to the item's modules (advisory rules appear as links only); the item and, for large features, its stages; the modules the item names; the role's rules, checklist and outputs; and a "load on demand" list. A `--budget N` trims bodies progressively until the prompt fits. `--explain` lists every document pulled in and why, and every rule skipped and why.

A role prompt has, in order: identity, scope, inputs it loads, rules, checklist, output format, stop conditions (see each `prompt-guide.md`).

## 8. Stack packs

A pack is a directory `packs/<name>/` with `pack.yaml` and optional `rules/*.md` and `templates/*.md.j2`. `pack.yaml` declares detection (`any_files`, `require_text`), a `priority`, the stack, build-tool `variants` each with workflow commands, and module discovery strategies (`gradle`, `maven`, `npm`, `dirs`). Pack rules are copied into the bundle as draft `rule` documents; pack templates override the kit's body templates. Adding a pack needs no code (`ackit init --pack-dir <dir>`). Shipped: java-spring, node-react, python, go, generic. Packs describe a technology; role profiles describe a way of working; neither depends on the other.

### Three layers, three names (only the role layer is a "profile")

| Concept | Is | Lives in |
|---|---|---|
| **Stack pack** | how a technology builds, tests and what rules it brings | `packs/<name>/` (section 8) |
| **Role profile** | how a working role operates (`role.yaml`, prompt, rules, checklist, outputs) | `<role>/` and the bundle's `roles/` (section 7) |
| **Adopter overlay** | one organisation's overlay: answers, import mapping, extra rules, role overlays | `adopters/<adopter>/` in the kit repository, or in the adopter's own repository |

The core of ACF names no company, repository, host or tool; code hosts and ticket tools appear only as neutral examples. Anything specific to an organisation belongs in its adopter overlay (`adopters/example/` is the starting point).

## 10. Gates

`ackit check --gate start|handoff --item <id> [--role <r>] [--json]` exits 0 on pass, 1 on fail. Each check is `pass`, `warn` or `fail`.

- **start**: item exists and is a work item; no validation errors in the item, its stages, modules, rules and entry; status `ready` or `in-progress` (`draft` allowed for planner); acceptance criteria present; `depends_on` all done; named modules exist; blocking rules verified (warn). With `--role`, the role must be known; not taking part in the gate is a warn.
- **handoff**: status `in-progress` or `in-review`; a passing `test-evidence`; a session entry mentioning the item; a journal (fail for features, warn otherwise); a review record that is not `blocked` (warn if absent); a security review (warn if absent).

## 11. Identity, naming, linking

- A concept's ID is its path without `.md`. Types with an `id` use the patterns in section 5; files start with the id (`F-001-export.md`) except `rule` and `module`, whose file is the slug (`rules/no-secrets.md` has id `R-no-secrets`).
- Links are markdown. Use bundle-root absolute paths (`/rules/no-secrets.md`). Frontmatter references use ids, or concept paths.
- Files are UTF-8, LF, one concept per file.
- **Id allocation (1.3).** `ackit new` takes the next number after the highest id of that type (`sequential`, the default). When several authors write on different branches, `id_allocation: {strategy: reserved-range, ranges: {<author>: [low, high]}}` in `ackit.yaml` gives each author a numeric range; `ackit new --author <name>` (or `$ACKIT_AUTHOR`) allocates inside it, continuing after the highest id in the range. A missing author, an author without a range and a full range are refused (exit 2) with a message; nothing is guessed, and there is no sequential fallback. `ackit ids assign <author> [--size N]` adds the next free range (default 1000 ids, after the highest existing range or at 1000) to `ackit.yaml`, touching only that line; the line must be merged to the shared branch before the author creates items (ADR-0020). Ranges must not overlap (ACF037). Ids stay numeric, so every id pattern is unchanged, and ACF009 still reports a duplicate after a merge.
- **Environment registry (1.3).** `ackit.yaml` may carry `environment_registry`: where code lives. Inline keys (named as the first part of each key path, by default `default_stage`, `repos`, `environments`, plus `extensions`; or the content of `source_file`, an opt-in read of one local file, relative to the bundle or absolute, possibly outside it) give `default_stage`, `repositories`, `environments` (`id`, one repository, an optional `code_line`, branches per stage and repository) and `extensions`, which the core carries and never reads. `key_paths` map an adopter's own file onto this model (`default_stage`, `repositories`, `environments`, `id`, `repository`, `code_line`, `branches` with `${stage}` and `${repo}`); the defaults are `default_stage`, `repos`, `environments`, `id`, `repo`, `code_line` and `stages.${stage}.branches.${repo}`, the generic shape agent-orchestly's yaml adapter reads. Inline data and `source_file` give the same model. The core only reads and validates (ACF038): no git, no network, no other file is opened. Absent block: nothing changes (ADR-0015, ADR-0016).
- **Branch policy (1.3).** `ackit.yaml` may carry `branch_policy`, separate from the registry. `work_branch` has `base_stage` (default: the registry's `default_stage`) and `name_pattern` (default `{author}-{environment}-{task}`). `context_branch` has `base` (`matching-code-base-branch`, the default, or `default-branch`), `fallback` (default `main`), `name_pattern` (default `{author}-{code_branch}`) and `required_before_code_push` (default false; the kit declares it, an adopter check enforces it). `ackit branch resolve --environment E [--repository R] [--stage S] [--author A] [--task T] [--code-base-branch B] [--code-branch C] [--existing-branch X ... | --existing-branches-file F] [--json]` prints the work branch base and name and the context branch base and name. The base of the context branch is the code base branch when the caller lists it among the existing store branches, otherwise the fallback. `--code-base-branch` defaults to the resolved work branch base, and the output states which value was used. Names are built by substitution; the caller checks they are valid git refs. It runs no git and no network: the caller supplies the branch list and creates the branches. Exit 0, 1 for an unknown environment, repository or stage, 2 for a missing or invalid configuration (ACF038, ACF039).
- **Code lines (1.3).** Any document may carry `code_lines: [id, ...]`, the code lines it is true for; absent or empty means every line. `ackit validate --code-line L` keeps only the findings of documents that apply to `L` (findings not tied to a document stay); `ackit prompt --code-line L` leaves out the rules, item modules and decisions that name lines and not `L` (the work item, journals and tech stack are never filtered). With a registry, `--code-line` must be a known line in both commands (exit 2 otherwise) and every id in `code_lines` must be known (ACF035). Branch per line remains the default; `code_lines` lets one document serve several lines (ADR-0017).
- **Author workspace (1.3).** `author_workspace: {root: "developers/{author}", in_index: false}` marks a folder per author. A document under it must carry `author` equal to its folder name (ACF036, warning). With `in_index: false` (the default) the generated `index.md` leaves workspace documents out and ACF024 does not ask for them to be listed; every other rule, including the journal and session format rules (ACF020, ACF021), still applies; a document that failed to parse or has no type is reported by ACF001 and ACF002 and not by ACF036. Absent block: nothing changes (ADR-0019).
- **Process checks (1.3).** `process_checks` is a list of `{name, level, when, run, description, timeout, stdin, scope}` the adopter writes; the core ships none. `{bundle}` and `{cwd}` inside a `run` argument are replaced by the bundle path and the working directory, `{tmpdir}` by a fresh temporary folder (removed after the run, also after a timeout), and `{git_command}` by the command line of the nearest `git` process above the hook (empty when there is none; Linux `/proc`, best effort), so a check can tell `git commit --amend` (plain text substitution, no shell). A failing check's own output is printed. `stdin: pass` gives the command the standard input of `ackit checks run`, read to the end once before the first check and given to every such command, so a pre-push hook's pushed refs reach it (default `none`: no input; a terminal gives an empty input; a caller that leaves standard input open without closing it makes the run wait, so hand-runs of such checks should use `< /dev/null`). A run that matches no check prints a warning and exits 0. `scope` is a free label: `--scope S` runs only the checks with that scope, no `--scope` runs only the unscoped ones, and `--name` of a check with another scope exits 2. `ackit checks run --when <pre-commit|pre-push|on-demand> [--name N] [--scope S] [--cwd DIR] [--json]` runs the entries for that point as argument lists without a shell, in the parent of the bundle (or `--cwd`), with `ACKIT_BUNDLE` and `ACKIT_CHECK_WHEN` in the environment and a timeout (default 120 seconds). A command runs without a shell, in its own process group, with the caller's environment (credentials included) plus the two variables; a timeout kills the whole group; only the last 64 KiB of output is kept. `--name` with a `--when` that is not the check's own point exits 2. A command that fails, cannot start or times out is a failure; a failing `block` check exits 1, a failing `warn` check is printed and exits 0; an invalid configuration exits 2 (ACF041). The commands may do anything the adopter decides, including network access (for example a store pull-request check before a code push); the core itself opens no connection, and `validate`, `branch resolve` and `checks run` are tested with socket creation, connection and name lookup and process spawning disabled, and a static test confirms that `src/ackit` imports no network library (a tripwire, not a formal proof; ADR-0016, ADR-0019).
- **Consumer layout (1.3).** Tools read a store at paths of their own, so the adopter lists them: `consumer_layout: {entry: AGENTS.md, entry_links: [...], rules_dir: rules, rules_links: [...]}`, where `entry` and `rules_dir` are inside the bundle and the links are paths relative to a target directory (for example a code clone). `ackit link --check [--target DIR] [--json]` reports each link as `ok` (a symlink to the bundle file or folder), `missing` or `wrong` (not a link, or a link elsewhere), and a configured source that is absent from the bundle as `missing`; it exits 1 unless every link is ok, 2 for an invalid configuration (ACF042), a missing bundle or a target that is the bundle itself (errors go to stderr, also with `--json`), and it creates nothing. A source missing from the bundle makes each of its links `missing`. `--check` is required: `ackit link` alone is refused, because creating links is not done by this command. A link path may not repeat or lie inside another (ACF042). Creation stays with `ackit init --link-entry` and the adopter's installer (ADR-0019).

## 12. Trust, staleness, provenance

An agent-written document starts `draft` with `generated.by` naming the agent. `stable`, `accepted` and similar trusted states require a `verified` entry whose actor starts with `human:` (ACF011). Editing a trusted document drops its `verified` entry until a human re-verifies (`ackit verify <path> --by human:<id>`). `--status signed-off` also writes `signoff: {by, at}`; `--signoff` writes it without a status change (for an item that needs a person's approval, such as a task above the auto-start limit). Both are refused unless the actor is `human:<id>` with a non-empty id, and an existing `signoff` is never overwritten. Types with facts that rot (`reference`, `runbook`, `rule`, `module`, `architecture`) get a default `review_by`. Imported material keeps its origin in `sources` and arrives `draft`.

## 13. Versioning

`acf_version` in root `index.md` frontmatter. A minor bump adds optional keys, types or rules (1.4 added the types `ticket-resolution`, `issue-pattern` and `platform-behaviour`, `vocabularies` with `vocab`, the `support` role, ACF043 to ACF045, a type-strict enum check and no default for a numeric enum in `ackit new`; 1.3 added `id_allocation`, `environment_registry`, `branch_policy`, `ackit branch resolve`, `code_lines`, `author_workspace`, `process_checks`, `ackit checks run`, `consumer_layout`, `ackit link --check`, ACF035 to ACF042; 1.2 added `points`, `runs`, `external_id`, ACF031 to ACF034; a 1.0 to 1.3 bundle validates unchanged except for the ACF045 warning on a session heading of another shape and the checks of bundles that already hold pages of the three support type names); a major bump may change required ones. Tools preserve unknown keys.
