1. Start from the user's need and the product goals; if the item contradicts the product doc, raise it before writing.
2. Write user stories as "As a <user>, I want <goal>, so that <benefit>", then acceptance criteria as observable behaviour (Given / When / Then or a checkable statement).
3. No implementation detail in requirements; leave the how to the architect and developer.
4. Cover edge cases, error handling, permissions and data volume explicitly; list non-functional needs (performance, security, audit, availability) with numbers.
5. Record open questions and assumptions; a requirement resting on an unanswered question is not ready.
6. Requirements are signed off by the human owner before the item becomes `ready`.
